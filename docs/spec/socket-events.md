# Socket.IO接続・イベント契約

## 概要

この文書は、タイムラインで使用するSocket.IOの接続認証、配信グループ、イベント名、送受信データ、配信対象、アクセス失効時の処理を定義します。データ更新を開始するREST APIは[タイムラインAPI](backend/api/timeline.md)と[ゲスト向けタイムラインAPI](backend/api/timeline-guest.md)、ルームへ入室できる条件は[ロール・権限仕様](roles-and-permissions.md)、フロントエンドの接続処理は[APIクライアント](frontend/api.md)を参照してください。

### 適用範囲

- デフォルト名前空間で接続するタイムライン用Socket.IO
- 接続時のユーザ／ゲスト認証とルーム認可
- バックエンドからフロントエンドへ送るアプリケーションイベント
- 再接続、アクセス再評価、強制切断時の現行動作

`connect`、`disconnect`、`error`、`connect_error`などSocket.IO自体が提供するライフサイクルイベントは、[フロントエンドの接続処理](#フロントエンドの接続処理)で扱います。投稿などの更新操作はREST APIで行い、Socket.IOを更新コマンドの受付経路には使用しません。

## 動作・適用条件

### 接続設定

| 項目 | 現行契約 |
| --- | --- |
| 接続先 | `API_BASE_URL`のオリジン。未設定時は`window.location.origin` |
| 名前空間 | デフォルト名前空間 `/` |
| パス | Socket.IO既定の`/socket.io/` |
| 生存確認 | バックエンドは`pingInterval=5000ms`、`pingTimeout=15000ms` |
| Engine.IO互換 | バックエンドは`allowEIO3=true` |
| 再接続 | フロントエンドはオプションを指定せず、`socket.io-client`の既定値を使用 |
| CORS | `SOCKET_CORS_ALLOWED_ORIGINS`を優先し、未設定時は`CORS_ALLOWED_ORIGINS`を使用 |

公開設定値の扱いは[フロントエンドビルド・設定](frontend/build-and-config.md)、バックエンド変数名は[環境変数](backend/environment-variables.md)を参照してください。

#### 接続時のクエリ

| クエリ | 必須 | 条件 |
| --- | --- | --- |
| `room_id` | 必須 | MongoDB ObjectId形式の有効なルームID |
| `lang` | 必須 | `ja`, `en`, `zh`, `pt`, `ko`, `vi`, `fr`, `es`, `sv`, `hi`, `it`, `ru`, `uk`, `de`, `tr`, `he`のいずれか |
| `user_token` | 条件付き必須 | ログインユーザのJWT。`guest_token`と同時指定不可 |
| `guest_token` | 条件付き必須 | ゲストアクセストークン。`user_token`と同時指定不可 |

`user_token`と`guest_token`は、必ずどちらか一方だけを送ります。フロントエンドはVuexにある両トークンを独立に追加し、排他性と`lang`の必須性を接続前に検証しません。不整合な場合はバックエンドが`connect_error`として接続を拒否します。

#### 接続認証と配信グループへの参加

バックエンドは次の順で接続を処理します。

1. `room_id`、`lang`、トークンの必須・形式・排他条件を検証する。
2. 論理削除されていないルームと所属フロアを取得する。
3. `user_token`ではJWTの署名・期限、有効なユーザ、`session_version`を検証し、DB上の現在の`User.role`でルームアクセスを判定する。
4. `guest_token`ではトークンと`guest_id`を検証し、`member_only=true`のルームへの接続を拒否する。
5. 全Socketはフロア・ルーム単位の認可管理用グループへ参加する。認証済みユーザはユーザ単位のグループにも参加し、セッション世代とルームアクセスを再確認する。ゲストもルーム・フロアの有効状態と公開状態を再確認し、許可された場合だけタイムライン配信グループへ参加する。
6. 対象ルームの配信グループへ参加したSocketを在室状況へ反映し、`ROOM_STATUS_UPDATE`を送信する。

接続時のミドルウェアで拒否した場合、フロントエンドは`connect_error`を受け取ります。認可管理用の配信グループへの参加後の再認可に失敗した場合は、対象ルームの配信グループと在室状況へ追加せず、バックエンドがそのSocketを強制切断します。

### 配信グループ

配信グループはSocket.IOの`room`であり、製品のルームとは別の概念です。タイムライン配信用にルームIDのグループを、認可管理用にユーザやフロア単位のグループを使用します。

| 配信グループ名 | 参加者 | 用途 |
| --- | --- | --- |
| `<room_id>` | 認可済みユーザとゲスト | タイムライン更新と在室状況の配信 |
| `__access__:room:<room_id>` | ユーザとゲスト | ルーム限定化・削除時の失効 |
| `__access__:floor:<floor_id>` | ユーザとゲスト | フロア削除時の失効 |
| `__access__:user:<user_id>` | 認証済みユーザ | 全フロアにまたがるロール変更・セッション失効通知と再認可 |
| `__access__:floor-user:<floor_id>:<user_id>` | 認証済みユーザ | 同一フロア内のメンバー関係変更・キック通知と再認可 |

`__access__:*`はバックエンド内部の配信先です。クライアントが任意に参加を要求するイベントは提供しません。

### 配信の共通契約

- アプリケーションイベントの方向は、すべてバックエンドからフロントエンドへの一方向である。
- タイムライン更新イベントは`io.to(<room_id>)`で送るため、発火元の利用者が接続しているSocketと同じ利用者の別タブも配信対象に含む。
- 更新イベントの第1引数は、原則として発火元サービスがREST応答にも使用する現在の`Chat`集約である。`replies`、投稿付加情報、返信付加情報は、多くの経路で論理削除済み要素を除外してから送る。
- `Chat`の参照データの展開（`populate`）状態は発火元サービスごとに完全には統一されていない。フロントエンドはイベント名と`_id`、配列構造を基準に反映し、固定のDTOバージョンは受け取らない。
- アプリケーション共通の受信確認（ack）、イベントID、通し番号、永続化、切断中イベントの再送は提供しない。返信の明示通知だけは、画面内カードの重複判定用に操作単位の`notification_event_id`を持つ。
- 非同期の翻訳と設定駆動AI解析はREST応答後に追加イベントを送ることがある。AI結果は通常の付加情報の作成または更新イベントを使用する。複数処理をまたぐアプリケーションレベルの全体順序は保証しない。
- 非同期翻訳は対象言語ごとに独立して処理し、一部が失敗しても成功した翻訳を更新イベントで反映する。失敗が1件以上ある場合は続けて`TRANSLATION_ERROR`を送る。
- タイムラインのDB保存後は、通知用データ生成・配信先取得・送信の例外をイベント別に記録し、保存済み操作のAPI応答や翻訳・解析結果の保存状態を失敗へ変えない。翻訳結果の更新イベントが送れなかった場合も、対象言語の翻訳失敗があれば`TRANSLATION_ERROR`の送信を試みる。
- 再接続成功時は全カラムの初回取得をやり直し、通常はREST APIで各カラムの最新10件を取得する。古い投稿は追加取得する。切断中の差分はこの再取得で反映し、イベントの再送は行わない。

### タイムライン更新イベント

この節のイベントは、すべてバックエンド→フロントエンド、対象`<room_id>`、送信者自身を含む配信です。表の`Chat`は第1引数の現在の`Chat`集約を表します。

| イベント | 発火条件 | 送受信データ | フロントエンド反映 |
| --- | --- | --- | --- |
| `POST_CREATE` | ユーザまたはゲストが投稿を作成 | `Chat` | 条件に一致するカラムの先頭へ追加し、効果音・読み上げを処理 |
| `POST_UPDATE` | 投稿更新、または本文の非同期翻訳完了 | `Chat` | 表示中の同一投稿を置換 |
| `POST_DELETE` | 投稿を論理削除 | `Chat` | `_id`が一致する投稿を各カラムから削除 |
| `SUPPLEMENT_CREATE` | 投稿付加情報の作成、または投稿の非同期解析完了 | `Chat` | 最新の投稿付加情報を読み上げ、同一投稿を置換 |
| `SUPPLEMENT_UPDATE` | 投稿付加情報の更新、または非同期翻訳完了 | `Chat` | 同一投稿を置換 |
| `SUPPLEMENT_DELETE` | 投稿付加情報の削除 | `Chat` | 同一投稿を置換 |
| `REPLY_CREATE` | ユーザまたはゲストが返信を作成 | `Chat` | 同一投稿を置換し、最新返信の効果音・読み上げ・通知カードを処理 |
| `REPLY_UPDATE` | 返信更新、または返信の非同期翻訳完了 | `Chat` | 同一投稿を置換し、`notify_all=true`の返信があれば通知カードを処理 |
| `REPLY_DELETE` | 返信を論理削除 | `Chat` | 同一投稿を置換 |
| `REPLY_SUPPLEMENT_CREATE` | 返信付加情報の作成、または返信の非同期解析完了 | 第1引数`Chat`、第2引数`Supplement|null` | 第2引数を読み上げ、同一投稿を置換 |
| `REPLY_SUPPLEMENT_UPDATE` | 返信付加情報の更新、または非同期翻訳完了 | `Chat` | 同一投稿を置換 |
| `TRANSLATION_ERROR` | 非同期翻訳の対象言語が1件以上失敗 | `{ failedLanguages: string[] }` | 技術詳細と言語コードを表示せず、表示言語に合わせたアラートを表示 |
| `REPLY_SUPPLEMENT_DELETE` | 返信付加情報の削除、または返信削除に伴う削除 | `Chat` | 同一投稿を置換 |
| `TAG_UPDATE` | 投稿または返信の`RoomTag`を更新 | `Chat` | 同一投稿を置換 |
| `REACTION_CREATE` | 投稿へリアクションを作成 | `Chat` | 同一投稿を置換し、条件を満たす場合は通知カードを処理 |
| `SUPPLEMENT_REACTION_CREATE` | 投稿付加情報へリアクションを作成 | `Chat` | 同一投稿を置換 |
| `REPLY_REACTION_CREATE` | 返信へリアクションを作成 | `Chat` | 同一投稿を置換 |
| `REPLY_SUPPLEMENT_REACTION_CREATE` | 返信付加情報へリアクションを作成 | `Chat` | 同一投稿を置換 |
| `REACTION_DELETE` | 4種類いずれかのリアクションを削除 | `Chat` | 同一投稿を置換 |

ログインユーザが返信の作成または編集で`notify_all=true`を指定した場合、バックエンドはSocket送信用に複製した対象返信へ次の一時フィールドを付与します。これらは`Chat`へ保存せず、RESTレスポンスにも含めません。

| フィールド | 契約 |
| --- | --- |
| `notify_all` | 明示通知が指定されたことを示す`true` |
| `notification_event_id` | 返信IDではなく通知付き送信操作ごとに生成する一意な文字列 |
| `notified_at` | 通知付き送信操作を処理した日時（ISO 8601文字列） |

フロントエンドは`notification_event_id`が同じイベントの再受信を重複表示せず、同じ返信でもIDが異なる別の通知付き編集はそれぞれ通知カードとして表示します。このIDは配送確認や順序保証、切断中イベントの再送には使用しません。IDがない場合は、返信の`notified_at`、`updated_at`、`created_at`、`_id`の順に、最初に値がある項目を通知カードの識別に使用します。

`REPLY_SUPPLEMENT_CREATE`は通常タイムライン、v1、解析サービスのいずれも2引数で送ります。第1引数は`Chat`です。
通常タイムラインとv1の第2引数は、保存した返信付加情報です。解析サービスも結果を保存した場合だけイベントを送り、
第2引数には保存後の`Chat`から解決した返信付加情報を指定します。古い世代の結果、適用済みの結果、削除済みデータ、競合、
または解析対象の不在により保存されなかった場合はイベント自体を送りません。解析サービスで保存後の`Chat`から対象を解決
できなかった場合に限り、第2引数は`null`になり得ます。この場合、フロントエンドの読み上げ処理が例外になり、同じイベントでの投稿表示の更新も完了しません。

### 在室状況イベント

#### `ROOM_STATUS_UPDATE`

| 項目 | 契約 |
| --- | --- |
| 方向 | バックエンド→フロントエンド |
| 発火条件 | 対象ルームの配信グループへの参加完了時、および接続切断時 |
| 対象 | `<room_id>`に残る全Socket。参加時は新しいSocket自身も含む |
| 送受信データ | `{ roomSize: number, languages: string[] }` |
| フロントエンド反映 | タイムラインヘッダーで使用するルーム状態へ設定し、参加者言語から翻訳対象を再計算する。切断時は状態を`null`へ戻す |

`roomSize`はSocket数ではなく、ユーザIDまたはゲストIDの異なる参加者数です。同じ利用者の複数タブは1人として数えます。`languages`は接続中Socketごとの言語を重複除外した一覧です。同じ利用者が異なる言語の複数タブを開いている間は両言語を保持し、切断時はそのSocketの言語だけを除きます。

### アクセス・セッションイベント

| イベント | 発火条件 | 対象 | 送受信データ | バックエンドの後続処理 | フロントエンド反映 |
| --- | --- | --- | --- | --- | --- |
| `RECEIVE_COMPLETE_DELETE_ROOM_MEMBER` | フロアメンバー／ルームメンバーの削除・脱退、またはユーザロール変更後の再評価で現在のルームへの権限を失った | 拒否された個々のSocket | なし | 通知直後に強制切断 | 現在のフロアのルーム一覧へ遷移 |
| `USER_ROLE_UPDATED` | 管理者がユーザのロールを変更 | `__access__:user:<user_id>` | `{ role: string }` | 全接続をルームごとに再評価し、拒否されたSocketへ上記失効イベントを送って切断 | ユーザロールを更新し、ルームロールを未設定にしてAPIから再取得 |
| `SESSION_REVOKED` | 本人変更・再設定・管理更新でパスワードを更新、またはユーザを論理削除。削除済み状態への再要求でも切断を再試行 | `__access__:user:<user_id>` | なし | 通知直後に対象ユーザの全Socketを強制切断 | エラー表示後にログアウトし、ログイン画面へ遷移 |
| `KICKED_USER` | 管理者または対象フロアを作成したフロア編集ユーザがユーザを対象フロアでキック | `__access__:floor-user:<floor_id>:<user_id>` | なし | 通知直後に対象フロアの全Socketを強制切断 | エラーを表示し、フロア一覧へ遷移 |

`ACCESS_REVOKED`は設定変更後に次のペイロードで通知して切断します。ログイン状態は維持し、フロントエンドは再接続処理を停止します。

| ペイロード | 対象 | 遷移先 |
| --- | --- | --- |
| `{scope: "room", reason: "room_restricted"}` | 公開からメンバー限定へ変更したルームのゲストと再評価で拒否されたユーザ | 現在フロアのルーム一覧 |
| `{scope: "room", reason: "room_deleted"}` | 削除したルームの全Socket | 現在フロアのルーム一覧 |
| `{scope: "floor", reason: "floor_deleted"}` | 削除したフロアの全Socket | フロア一覧 |

ルーム・フロアの設定変更に伴う失効は、通常操作と管理操作に共通です。非表示設定だけの変更、公開化、復元では切断しません。DB更新成功後に失効を行い、通知失敗時も切断を試みます。これらの設定変更とパスワード更新では、Socket処理の例外を記録し、保存済みのAPI成功を失敗へ変えません。パスワード更新時の失効は、通知メールと残存再設定トークンの削除より先に行います。

アクセス再評価では、現在も公開ルームへ入室できる、または別のフロアメンバー／ルームメンバー権限を持つSocketを維持します。Socket一覧取得や認可照会に失敗した場合は、アクセスを推測で維持せず対象接続を安全側で切断します。バックエンドは通知後の受信確認を待たずに切断します。

メンバー削除・脱退、ユーザロール変更、ユーザ論理削除でも、通知失敗は記録して切断を続行します。これらの操作で切断自体が失敗した場合は、ほかの拒否対象の切断も試みたうえでAPIへエラーを返します。ユーザ論理削除とロール変更では、同じ状態の要求でも切断・再評価を再試行します。キックは通知・切断の失敗を個別に記録し、保存後のAPI成功を維持します。

### フロントエンドの接続処理

- 接続タイムアウトと再接続回数・間隔はライブラリの既定値で、サービスの復旧目標および一時障害／再接続終端の判定契約を固定していない
- 期限切れ・無効トークン、ルーム不存在、権限拒否をフロントエンドが安全に機械判定できる構造化されたSocket認証エラーコードを固定していない

- 新しいタイムライン接続を作る前に、以前のSocketのイベントハンドラを解除して以前のSocketを切断する。ブラウザ復帰リスナーは認証回復中も維持し、画面内で1組だけ登録する。
- `connect`時は接続済み状態にし、保存済みフィルタを正規化したうえで、各カラムをREST APIから初回取得する。
- `error`、`connect_error`、`disconnect`時は未接続状態にし、画面が可視なら800ms後に接続状態を表示する。非表示中は表示しない。
- 手動再接続と絞り込みクエリ変更は状態にかかわらず以前のSocketを破棄する。自動復旧は`disconnect`、`visibilitychange`、`pageshow`、`online`から要求し、同時要求では進行中のPromiseを共有する。ただし`io server disconnect`と`io client disconnect`から自動復旧しない。
- `connecting`が実経過30秒以上続いた場合はSocketを作り直す。接続監視処理は非表示中に再生成せず、復帰時はブラウザタイマーではなく接続開始時刻との差で判定する。
- ゲストの再接続ではSocket生成前にゲストトークンの更新を行い、`401 TOKEN_INVALID`または`401 TOKEN_EXPIRED`の場合だけ初期認証へ切り替える。それ以外の失敗ではゲストIDを維持し、Socketを生成しない。
- 古いSocketから遅れて届いたイベントは、現在のSocketと一致しない場合に無視する。
- 再接続処理は世代で管理し、旧世代の認証結果、Socketイベント、表示タイマーを無視する。タイムライン画面の破棄時は世代を無効化し、ハンドラとリスナーを解除してSocketを切断する。

### クライアントからバックエンドへのイベント

フロントエンドからバックエンドへ送るアプリケーションイベントはありません。メンバー削除・脱退はREST APIで処理し、成功後にバックエンドが現在のアクセス権を再評価します。
