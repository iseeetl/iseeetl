# スパム管理（/management/spam）

## 概要

- タイムラインの投稿・返信・付加情報本文へ適用するスパムワードをAdministratorが作成・更新・物理削除する
- 設定変更は次回以降の本文作成・更新から反映し、保存済み本文を遡って再置換しない
- スパム検出件数、置換履歴、対象投稿、作成者別の監査、設定の復元は扱わない

## 利用条件・開き方

- 入口はアプリメニューの管理者向け「スパム管理」、またはURLへの直接アクセスである

### URL

| 項目 | 値 |
| --- | --- |
| パス | `/management/spam` |
| ルート名 | `SpamManagement` |
| コンポーネント | `frontend/src/views/management/SpamManagement.vue` |
| メタ情報 | `isManagement: true` |

- アプリメニューはVuex上のロールが`Administrator`の場合だけ「スパム管理」を表示する
- ルートガードはlocalStorageから状態を復元し、ログイン済みAdministratorだけを通過させる
- 未ログインまたはAdministrator以外が直接アクセスした場合はログアウト処理を行い、`/login`へ遷移する
- ルートメタ情報に画面タイトルはなく、文書タイトルにはアプリ名だけを設定する

### 利用条件

| 利用者 | アプリメニュー | 画面遷移 | スパム管理API |
| --- | --- | --- | --- |
| Administrator | 表示 | 可 | 可 |
| Editor／Author／developer | 非表示 | ログアウト後ログイン画面へ遷移 | 403 |
| ゲスト／未ログイン | 非表示 | ログイン画面へ遷移 | 401 |

- バックエンドはJWT検証時に有効なユーザと`session_version`を確認し、現在のDBロールで認証情報を上書きした後、ミドルウェアでAdministratorを確認する
- Spam サービスでは操作者ユーザを再取得せず、認可はJWT ミドルウェアと管理者ミドルウェアへ依存する
- API契約と本文置換の詳細は[スパム管理API](../../backend/api/spam.md)を参照する

## 画面構成

- H1「スパム管理」
- 「作成」ボタン
- 管理一覧の共通配置に従う検索欄
- スパムワード一覧テーブル
  - スパムワード
  - 作成日
  - 「削除」「編集」の順に並ぶ明示的な操作
- 新規作成と更新で共用し、用途に応じてタイトルが変わるダイアログ
  - スパムワード入力
  - 編集時の対象スパムワード表示
  - PC フッターとモバイルヘッダーの「キャンセル」「作成／保存」
- 対象語を表示する「スパムワード削除」確認ダイアログ
- 作成・更新・削除の処理中に表示する進捗
- 共通の一覧状態・ページャと、作成・更新・削除エラー用スナックバー
- 作成者、更新日時、使用件数、置換対象、重複状態、削除履歴は表示しない

## 操作と動作

### 初期表示・一覧・検索・ページング

- 一覧の共通状態、検索フォーム、ページャ、URL履歴、競合要求、ページ補正は[管理一覧・検索共通仕様](../management-list.md)に従う
- 初期表示は`GET /api/spam/management/paginate?page=1&search=`を呼び出す
- 1ページ10件で、Spamを`created_at`降順に表示する
- 検索語はフロントエンドとバックエンドで前後の空白を除去し、空文字は検索条件なしとして扱う
- 検索時は正規表現の特殊文字を通常文字として扱い、`word`を大文字・小文字を区別せず部分一致検索する
- フロントエンドは1〜50文字を入力条件とし、範囲外の検索要求を送らない。バックエンドも50文字超過を400で拒否する

### 作成・更新

- 「作成」はIDを持たない空の編集ダイアログを開く
- 行内の明示的な「編集」ボタンは、選択SpamのIDとwordを編集ダイアログへ反映する。行全体は操作対象にしない
- 入力変更後の閉じる要求では破棄確認を表示する。送信中は閉じる要求を拒否する
- wordは必須で、前後の空白除去後1〜50文字を要求する。フロントエンドとバックエンドの制約は一致する
- IDがあれば`POST /api/spam/management/update`、なければ`POST /api/spam/management/create`へ前後の空白を除去済みwordを送る
- 作成時はJWTのユーザIDを`Spam.user`へ保存する。更新では元の作成者と`created_at`を変更しない
- 同一word、大文字・小文字だけが異なるword、包含関係にあるwordも重複して保存できる
- `sending=true`の間は入力、キャンセル、「作成／保存」を無効にし、Escape、背景クリック、二重要求によるダイアログを閉じる操作と再送を抑止する
- 作成・更新APIの開始から現在ページの再取得終了までは、ダイアログのタイトルで名前付けした処理中の案内を表示し、対象IDとwordを維持する
- API成功後は現在ページの再取得終了を待ち、`sending`を解除してからダイアログと編集値をクリアする
- API失敗時は一覧を再取得せず、作成時は`作成に失敗しました`、更新時は`更新に失敗しました`とAPIエラーコードに対応する翻訳済みの詳細を表示し、編集ダイアログと入力値を維持して再操作できる状態へ戻す
- API成功後の一覧再取得失敗は作成・更新エラーとして再表示せず、共通一覧のエラー表示と再試行へ委ねてダイアログを閉じる

### 物理削除

- 一覧行の「削除」で、対象wordと復元不能であることを表示する削除確認ダイアログを開く
- 確認後はSpam IDだけを`POST /api/spam/management/delete`へ送る
- `sending=true`の間は削除確認のキャンセルとOKを無効にし、Escape、背景クリック、二重要求によるダイアログを閉じる操作と再送を抑止する
- 削除APIの開始から現在ページの再取得終了までは、ダイアログのタイトルで名前付けした処理中の案内を表示し、削除確認ダイアログと対象ID・wordを維持する
- バックエンドはスパムワードを物理削除し、復元情報を保持しない。画面はAPI成功後に現在ページの再取得終了を待ってから`sending`を解除し、両ダイアログと編集値をクリアする
- API失敗時は一覧を再取得せず、`削除に失敗しました`とAPIエラーコードに対応する翻訳済みの詳細を表示し、削除確認ダイアログと対象wordを維持して再操作できる状態へ戻す
- API成功後の一覧再取得失敗は削除エラーとして再表示せず、共通一覧のエラー表示と再試行へ委ねてダイアログを閉じる
- 更新・削除対象がすでに存在しない場合、バックエンドは200 `null`を返し、画面は成功として閉じる
- 401では共通一覧処理がログイン画面へ遷移する

### タイムライン本文への反映

- スパムワードの設定はユーザ／ゲストの投稿、返信、投稿付加情報、返信付加情報の作成時と本文更新時に適用する
- 保存されている全スパムワードを長い順に並べ、正規表現の特殊文字をエスケープして、大文字・小文字を区別せず一致箇所を`***`へ置換する
- 設定の作成・更新・削除はキャッシュを介さず、次の本文処理から反映する
- 設定変更前に保存された本文、翻訳、通知、既存クライアント表示を再処理しない
- スパムワードの作成・更新・削除はSocket.IOイベントを送信せず、製品内の操作履歴も記録しない

## 通信・エラー時の動作

### 使用するAPI

| 目的 | Method / Path | 主な送信値 | 画面での扱い |
| --- | --- | --- | --- |
| ページング一覧 | `GET /api/spam/management/paginate` | クエリ: `page`, `search` | `docs`, `total`, `pages`, `page`を一覧とページャへ反映 |
| 作成 | `POST /api/spam/management/create` | 本文: `word` | 成功後に現在ページを再取得 |
| 更新 | `POST /api/spam/management/update` | 本文: `_id`, `word` | 成功後に現在ページを再取得 |
| 物理削除 | `POST /api/spam/management/delete` | 本文: `_id` | 成功後に現在ページを再取得 |

- ページングルートはGET／POSTを受け付け、現行フロントエンドはGETを使用する
- 更新・削除APIは結果を返すが、画面は応答データを使用せず一覧を再取得する

### 読み込み中・データなし・エラー時

- 初回読込、更新中、空、取得失敗、前回結果を保った失敗、再試行は[管理一覧・検索共通仕様](../management-list.md)に従う
- 一覧取得の失敗は画面内に表示し、作成・更新・物理削除の失敗はスナックバーで通知する
