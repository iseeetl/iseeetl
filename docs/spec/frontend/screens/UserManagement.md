# ユーザ管理（/management/user）

## 概要

- サイト全体のユーザをAdministratorが横断参照し、ユーザ名、メール、パスワード、システムロールを更新する
- 論理削除状態は状態絞り込み条件で参照範囲を切り替え、行の明示的な削除・復元操作で変更する
- ユーザの新規登録、外部認証連携、プロフィール画像・言語・通知設定の編集、物理削除は行わない

## 利用条件・開き方

- 入口はアプリメニューの管理者向け「ユーザ管理」、またはURLへの直接アクセスである

### URL

| 項目 | 値 |
| --- | --- |
| パス | `/management/user` |
| ルート名 | `UserManagement` |
| コンポーネント | `frontend/src/views/management/UserManagement.vue` |
| メタ情報 | `isManagement: true` |

- アプリメニューはVuex上のロールが`Administrator`の場合だけ「ユーザ管理」を表示する
- ルートガードは遷移時にlocalStorageから状態を復元し、ログイン済みAdministratorだけを通過させる
- 未ログインまたはAdministrator以外が直接アクセスした場合はログアウト処理を行い、`/login`へ遷移する
- ルートメタ情報に画面タイトルはなく、文書タイトルにはアプリ名だけを設定する

### 利用条件

| 利用者 | アプリメニュー | 画面遷移 | 管理一覧・更新API |
| --- | --- | --- | --- |
| Administrator | 表示 | 可 | 可 |
| Editor／Author／developer | 非表示 | ログアウト後ログイン画面へ遷移 | 403 |
| ゲスト／未ログイン | 非表示 | ログイン画面へ遷移 | 401 |

- 一覧・更新APIはJWT上のAdministratorをミドルウェアで確認し、サービスでもJWTのユーザIDに対応する有効なユーザと現在のDBロールがAdministratorであることを再確認する
- JWT検証はユーザが有効で、JWT内とDB上の`session_version`が一致することを要求し、現在のDBロールで認証情報を上書きする
- 既存Administratorはユーザ名、メール、パスワードを更新できるが、ロール変更と論理削除はフロントエンドとバックエンドの両方で禁止する
- Administratorへの新規昇格はできず、管理画面から割り当てられるロールは`Author`、`Editor`、`developer`に限る
- 横断的な権限は[ロール・権限仕様](../../roles-and-permissions.md)、API契約は[ユーザ API](../../backend/api/user.md)を参照する

## 画面構成

- H1「ユーザ管理」
- 管理一覧の共通配置に従う検索欄
- 状態絞り込み条件（すべて／未削除／削除済み）
- ユーザ一覧テーブル
  - ユーザ名
  - メール
  - 権限
  - 状態
  - 作成日
  - 更新日
  - 削除日
  - 明示的な編集・削除・復元操作
- 有効ユーザの「編集」ボタンで開く「ユーザ編集」ダイアログ。行全体は操作対象にしない
  - ユーザ名
  - メール
  - 新しいパスワード
  - 権限
  - 「キャンセル」「保存」
- 対象ユーザ名と復元可能であることを示す削除・復元確認ダイアログ
- 更新処理中に表示する進捗
- 共通の一覧状態・ページャと、ユーザ更新エラー用スナックバー
- ユーザID、プロフィール画像、言語、表示・通知設定、`session_version`、外部認証種別、所属フロア／ルームは表示しない

## 操作と動作

### 初期表示・一覧・検索・ページング

- 一覧の共通状態、検索フォーム、ページャ、URL履歴、競合要求、ページ補正は[管理一覧・検索共通仕様](../management-list.md)に従う
- 初期表示は`GET /api/user/management/paginate?page=1&search=`を呼び出し、未削除と削除済みを取得する
- 1ページ10件で、ユーザを`created_at`降順で表示する。状態の絞り込みは共通仕様に従う
- 検索語がある場合、ユーザ名またはメールを大文字・小文字を区別せず、正規表現の特殊文字をエスケープした部分一致で検索する
- 検索語は前後の空白を除去せず、前後の空白も検索条件に含める
- フロントエンドは2〜20文字を入力条件とし、範囲外の検索要求を送らない
- バックエンドは最大20文字だけを検証し、1文字検索を受け付けるため、フロントエンドの最小2文字とは差がある
- メールが`null`の場合と未知のロールは`—`で表示する。同名でメールも未設定のユーザは、一覧の名前とメールだけでは区別できない

### 編集ダイアログ

- 有効な行の「編集」を選択すると一覧の`_id`、`username`、`mail`、`role`、`image_name`、`delete_flg`を編集状態へコピーする
- 有効行の操作は「削除」「編集」の順に表示し、削除済み行は「復元」だけを表示する
- 編集ダイアログには対象ユーザ名を固定表示し、PCではフッター、モバイルではヘッダーにキャンセル／保存操作を配置する
- パスワードは一覧応答に含まれず、ダイアログの入力値に設定しない
- `Administrator`を選択した場合、権限は「管理者」の読み取り専用入力とする。Administratorの行には削除・復元ボタンを表示しない
- それ以外のユーザでは「投稿者」「フロア編集者」「開発者」だけを選択できる
- 未変更のキャンセルまたはダイアログ外クリックでは閉じ、入力変更後は破棄確認を表示する。送信中は閉じる要求を拒否する
- 更新確認ダイアログはなく、「保存」で直ちに更新する。編集ダイアログに論理削除チェックボックスは表示しない

### 入力と送信ペイロード

| 項目 | フロントエンド検証 | バックエンド検証・保存 |
| --- | --- | --- |
| ユーザ名 | 必須、2〜20文字 | 必須、1〜20文字。前後の空白除去・一意性検査なし |
| メール | `null`またはメール形式。空文字は不可 | `null`または100文字以内のメール形式。文字列は前後の空白除去・小文字化し、論理削除済みを含むユーザと重複不可 |
| 新しいパスワード | 任意、指定時8〜16文字 | 任意、指定時8〜16文字。bcryptでハッシュ化 |
| 権限 | `Author`／`Editor`／`developer` | 変更先は同じ3種類。既存Administratorは`Administrator`を維持 |
| 論理削除 | 編集対象の元の真偽値を保持 | 真偽値 |

- `_id`と`mail`は常に送る。ユーザ名、ロール、プロフィール画像名、論理削除状態はフロントエンドの編集値が`null`でなければ送り、パスワードは空でない場合だけ送る
- `image_name`は一覧値をそのまま送ることがあるが、管理更新ルートの検証項目とサービスの更新対象には含まれず、バックエンドは変更に使用しない
- `sending=true`の間は各入力、権限、キャンセル、保存ボタンを無効にし、Escape、背景クリック、二重要求によるダイアログを閉じる操作と再送を抑止する
- 更新APIの開始から現在ページの再取得終了までは、ダイアログのタイトルで名前付けした処理中の案内を表示し、編集ダイアログ、対象ユーザ、入力値を維持する
- API成功後は現在ページの再取得終了を待ち、`sending`を解除してからダイアログと編集状態をクリアする
- API失敗時は一覧を再取得せず、`更新に失敗しました`とAPIエラーコードに対応する翻訳済みの詳細をスナックバー表示し、ダイアログと入力値を維持して再操作できる状態へ戻す
- API成功後の一覧再取得失敗は更新エラーとして再表示せず、共通一覧のエラー表示と再試行へ委ねてダイアログを閉じる
- 401では共通エラー処理がログアウトし、ログイン画面へ遷移する

### パスワード変更・論理削除・復元

#### パスワード変更

- パスワードを指定すると、同じユーザ更新内で`session_version`を1増分して、変更前に発行済みの全JWTを失効させる
- 管理更新APIは対象ユーザ用の新JWTを返さないため、対象ユーザは新しいパスワードで再ログインする必要がある
- パスワード更新成功直後に対象ユーザの全Socketへ`SESSION_REVOKED`を送り、全接続を切断する。ロールも同時に変えた場合はセッション失効を優先する
- Administratorが自分自身のパスワードをこの画面で変更した場合、更新成功後の一覧再取得は旧JWTを使用するため401となり、共通処理でログアウトする

#### 論理削除

- 有効な行の「削除」は対象ユーザ名と復元可能であることを示す確認ダイアログを開く。確定後は`POST /api/user/management/delete-state`へ`_id`と`delete_flg=true`だけを送る
- 有効ユーザを論理削除すると`deleted_at=現在日時`へ変更し、`session_version`を1増分する
- 有効なAI解析設定が対象ユーザを結果ユーザとして参照中の場合、削除は409で拒否する
- 対象ユーザの全Socketへ`SESSION_REVOKED`を通知して切断し、旧JWTと旧Socketによる再接続を拒否する
- 並行した削除要求は有効状態を条件に更新し、後から競合した要求は409を返す。すでに削除済みのユーザへ削除状態を再送した場合は世代を増分せず、Socket切断だけを再試行する
- 論理削除はユーザに紐づくフロア、ルーム、メンバー、投稿その他の関連データを連鎖削除しない

#### 復元

- 削除済み行の「復元」は対象ユーザ名を示す確認ダイアログを開く。確定後は状態専用APIへ`_id`と`delete_flg=false`だけを送り、`deleted_at=null`へ戻す
- 復元では`session_version`を戻さないため、削除前JWTは再び有効にならない
- 復元成功時に新JWTは発行せず、Socketを自動再接続しない。対象ユーザは再ログインする
- 削除・復元の送信中と成功後の一覧再取得中は対象を維持し、失敗時はダイアログを開いたまま再操作できる

## 通信・エラー時の動作

### ロール変更とSocket再評価

- ロール変更だけでは`session_version`を増分せず、変更前JWTは継続して使用できる
- 後続のREST要求ではJWT内の旧ロールではなくDB上の現在ロールを使用する
- パスワードを変更しない更新の成功後、対象ユーザの全Socketへ`USER_ROLE_UPDATED`を通知し、接続先ルームごとに現在のロールと所属からアクセスを再評価する
- 同じロールを維持した更新でも再評価を行うため、DB更新後にSocket処理だけが失敗した場合は同じ内容を保存し直して再試行できる
- 権限を失ったSocketだけへ`RECEIVE_COMPLETE_DELETE_ROOM_MEMBER`を通知して切断し、公開ルームや別の有効なメンバー権限で入室できる接続は維持する
- ロール変更は既存のフロア／ルーム作成者、フロアメンバー、ルームメンバー、投稿などの所有・所属レコードを変更しない
- Socket再認可の共通契約は[Socket.IOイベント仕様](../../socket-events.md)を参照する

### 使用するAPI

| 目的 | Method / Path | 主な送信値 | 画面での扱い |
| --- | --- | --- | --- |
| ページング一覧 | `GET /api/user/management/paginate` | クエリ: `page`, `search`, 任意 `delete_flg` | `docs`, `total`, `pages`, `page`を一覧とページャへ反映 |
| ユーザ更新 | `POST /api/user/management/update` | 本文: `_id`, `username`, `mail`, 任意の`password`, `role`, 元の`delete_flg` | 成功後に現在ページを再取得 |
| 削除・復元 | `POST /api/user/management/delete-state` | 本文: `_id`, `delete_flg` | 状態だけを変更し、成功後に現在ページを再取得 |

- ページングルートはGET／POSTを受け付け、現行フロントエンドはGETを使用する
- 更新APIは変更後ユーザを返すが、画面は応答データによる行置換を行わず一覧を再取得する
- 管理更新では変更理由や製品内の操作履歴を記録せず、本人への通知メールも送らない
- 409のメール重複、Administrator保護、ロール制約、AI解析設定からの有効参照は共通エラー詳細としてスナックバーへ追加表示する

### 読み込み中・データなし・エラー時

- 初回読込、更新中、空、取得失敗、前回結果を保った失敗、再試行は[管理一覧・検索共通仕様](../management-list.md)に従う
- 一覧取得の失敗は画面内に表示し、ユーザ更新の失敗はスナックバーで通知する
- 更新成功後は前回一覧を残した「更新中です」の状態で現在ページを再取得し、再取得終了後にダイアログを閉じる
