# ルーム管理（/management/room）

## 概要

- 全ルームをサイト管理者が横断参照し、既存ルームの内容、画像、利用設定、一覧表示状態を更新する
- 論理削除状態は状態絞り込み条件で参照範囲を切り替え、行の明示的な削除・復元操作で変更する
- この管理画面は既存ルームの更新専用であり、ルームの新規作成、所属フロア変更、物理削除は行わない

## 利用条件・開き方

- 入口はアプリメニューの管理者向け「ルーム管理」、またはURLへの直接アクセスである

### URL

| 項目 | 値 |
| --- | --- |
| パス | `/management/room` |
| ルート名 | `RoomManagement` |
| コンポーネント | `frontend/src/views/management/RoomManagement.vue` |
| メタ情報 | `isManagement: true` |

- アプリメニューはVuex上のロールが`Administrator`の場合だけ「ルーム管理」を表示する
- ルートガードは遷移時にlocalStorageから状態を復元し、ログイン済みAdministratorだけを通過させる
- 未ログインまたはAdministrator以外が直接アクセスした場合はログアウト処理を行い、`/login`へ遷移する
- ルートメタ情報に画面タイトルはなく、文書タイトルにはアプリ名だけを設定する

### 利用条件

| 利用者 | アプリメニュー | 画面遷移 | バックエンド管理API |
| --- | --- | --- | --- |
| Administrator | 表示 | 可 | 可 |
| Editor／Author／developer | 非表示 | ログアウト後ログイン画面へ遷移 | 403 |
| ゲスト | 非表示 | ログイン画面へ遷移 | 401 |

- バックエンドはJWTとサイト管理者ロールをミドルウェアで確認し、サービスでもJWTのユーザ IDから有効なAdministratorを再確認する
- 現在のAdministratorは作成者やフロアメンバーかどうかにかかわらず、論理削除済みを含む全ルームを更新できる
- 通常のルーム画面ではAdministrator、対象フロア作成者であるEditor、フロアメンバーがルームを更新でき、この画面は全体管理用の別経路である
- 詳細なAPI契約は[ルーム API](../../backend/api/room.md)、通常画面の挙動は[ルーム画面仕様](Room.md)を参照する

## 画面構成

- H1「ルーム管理」
- ラベル「検索」の検索欄
- 状態絞り込み条件（すべて／未削除／削除済み）
- 全ルームを横断する一覧テーブル
  - ルーム名
  - 所属フロア名
  - 作成ユーザ名
  - 作成日
  - 更新日
  - 削除日
  - 状態（有効／削除済み、表示／非表示、公開／メンバー限定）
  - 操作
- 通常のルーム一覧と同じタイトル、対象表示、入力区分、操作配置を使用し、`EditRoomDialog`を管理モードで使用する編集ダイアログ
- 共通の一覧状態・ページャと、編集結果用の共通ストアスナックバー
- 作成ボタン、フロア絞り込みUI、表示・公開状態の絞り込み、物理削除操作はない

## 操作と動作

### 初期表示・一覧・検索・ページング

- 一覧の共通状態、検索フォーム、ページャ、URL履歴、競合要求、ページ補正は[管理一覧・検索共通仕様](../management-list.md)に従う
- 初期表示は`GET /api/room/management/paginate?page=1&search=`を呼び出し、未削除と削除済みを取得する
- 1ページ10件で、ルームを`created_at`降順で表示する。状態の絞り込みは共通仕様に従う
- バックエンドは作成ユーザの`username`と所属フロアの`title`をpopulateし、それぞれ一覧へ表示する
- 表示／非表示は状態欄に表示する。`guest_reaction_only`、`notification`、`external_sns_button`、説明、画像の有無は一覧へ表示しない
- 検索は原文のタイトルまたは説明を対象とする、大文字・小文字を区別しない部分一致である
- バックエンドは正規表現の特殊文字をリテラルとして扱うが、検索文字列の前後空白は除去しない
- フロントエンドは2〜100文字を入力条件とし、範囲外の検索要求を送らない。バックエンドの上限は100文字で、空検索は`search=`で送る
- バックエンドAPIは任意の`floor_id`による絞り込みを持つが、この画面はフロア選択UIを持たず、値も送信しない

### 編集ダイアログ

- 有効な行の明示的な「編集」で、選択ルームの値を設定して「ルームを編集」ダイアログを開く。行全体は操作対象にしない
- 見出し直後に「対象ルーム」と変更前のルーム名を表示し、ダイアログの説明として関連付ける
- 入力は「基本情報」「画像」「参加・投稿設定」「表示・通知」の4区分とする。PCでは共通幅480pxでキャンセルと保存を右側へ隣接し、スマートフォンでは左右の上部操作へ切り替える
- 入力・操作項目は次のとおりである
  - タイトル: 必須、最大100文字
  - 説明: `null`または最大200文字
  - ルーム画像の選択、選択取消、登録済み画像の削除
  - `guest_reaction_only`: 「ゲストはリアクションのみ」
  - `member_only`: 「招待メンバーのみ」
  - `notification`: 「タイムライン最上部に通知する」
  - `external_sns_button`: 「外部SNS連携ボタンを表示する」
  - `room_display_hidden`: 「非表示にする」
- この管理画面からは`showLifecycleControl=false`を渡し、編集ダイアログ内に論理削除チェックボックスを表示しない。編集ペイロードは対象の元の`delete_flg`を維持する
- 所属フロア、原文言語、翻訳の編集欄はない
- フロントエンドは既存`lang`を管理更新ペイロードへ含め、バックエンドも原文言語として検証・保存する
- 管理モードでの確定には一覧から渡された既存ルームの`_id`を必須とする。対象IDがない状態で確定しても、画像アップロード、作成、更新、成功通知を行わない
- 入力、画像、参加・投稿設定、表示・通知設定を変更してからキャンセル、Escape、外側クリックを行うと破棄確認を表示する。変更していない場合と開始状態へ戻した場合は確認せず閉じる
- 保存成功後はダイアログ状態を初期化し、同じページと検索条件で一覧を再取得する
- 保存中は入力、画像操作、各設定チェック、キャンセル、保存、Escape、外側クリックを抑止し、進捗バーを表示する

### 各設定の意味

- `member_only`はルームへの入室認可に使用し、`room_display_hidden`は通常一覧の表示範囲を制御する
- `room_display_hidden`だけではIDを知る利用者の直接入室を拒否しない
- `guest_reaction_only`はゲストのタイムライン操作をリアクションに限定する
- `notification`はタイムライン最上部への通知表示、`external_sns_button`は外部SNS連携ボタンの表示を制御する
- この管理一覧はこれらの設定にかかわらずルームを取得する

### 翻訳・論理削除・復元・接続

- 管理更新時の翻訳は[翻訳の生成と更新](../style-and-i18n.md#翻訳の生成と更新)に従う。Google Translateが有効でタイトル、説明、`lang`のいずれかが変わった場合に、所属フロアの`target_langs`で再生成する
- 有効な行は削除、編集の順、削除済み行は復元だけを表示する。対象名と復元可能であることを示す確認ダイアログの後、状態専用APIへ`_id`と`delete_flg`だけを送る
- `delete_flg=true`では`deleted_at`を現在日時へ設定し、`false`では`deleted_at=null`としてルームだけを復元する。確認ダイアログの状態と再取得は[共通仕様](../management-list.md#論理削除復元の確認)に従う
- 有効なルームAI解析設定が存在してもルームを削除できる。ルームの論理削除・復元は配下の投稿、ルームタグ、ルーム単語、ルームAI解析設定、ルームメンバー、メディアの削除状態を変更しない
- ルームが論理削除中は配下のAI解析設定を利用できず、復元後は有効な設定を既存状態のまま再び利用できる
- 所属フロアが論理削除済みのルームは復元ボタンを無効にし、理由と関連付ける。バックエンドもこの復元を409で拒否するため、フロアを先に復元する
- 公開からメンバー限定への変更ではゲストと権限を失った接続を、論理削除では対象ルームの全接続を`ACCESS_REVOKED`で切断する。対象タイムラインはログイン状態を維持してルーム一覧へ遷移する
- ゲスト投稿制限、表示、通知、外部SNSの変更は既存接続を切断しない。公開化・復元も切断しない
- 管理更新は製品内の操作履歴を記録しない

### 画像処理と保存順序

- フロントエンドはJPEG／PNGを受け付け、選択画像を縦横最大400px、品質0.5のJPEG Blobへ変換し、変換後3MB以下を確認する
- バックエンドは画像署名、実形式、デコード可否、画素数などを再検査し、メタデータを引き継がず公開領域へ再エンコードする
- 新画像がある場合は、先に`POST /api/fileupload/room/image`で保存し、その画像名を管理更新APIへ送る
- 画像名が変化した場合はルームのDB更新後に旧画像を削除し、ファイルの削除に失敗しても更新は成功し、ファイルが残る場合がある
- 登録済み画像の削除は`image_name=null`を管理更新APIへ送り、DB更新後に旧画像ファイルを削除する
- 保存済み画像と選択中画像の分離、取消・削除、同じファイルの再選択、保存失敗時の状態は[保存済み画像の差し替えと取消](../media-input.md#保存済み画像の差し替えと取消)に従う

- 画像アップロードAPIは有効なルームと有効な所属フロアだけを受け付けるため、削除済みフロア配下での画像変更はアップロード段階で失敗する
- 画像の共通契約は[メディア入力制約](../media-input.md)と[ファイルアップロードAPI](../../backend/api/upload.md)を参照する

## 通信・エラー時の動作

- 画像アップロード後に管理更新が失敗すると、未参照画像が残る

### 使用するAPI

| 目的 | Method / Path | 主な送信値 | 画面での扱い |
| --- | --- | --- | --- |
| ページング一覧 | `GET /api/room/management/paginate` | クエリ: `page`, `search`, 任意 `delete_flg` | `docs`とページ情報を反映 |
| ルーム画像保存 | `POST /api/fileupload/room/image` | multipart: `floor_id`, `_id`, `image_file` | 新画像がある場合だけ管理更新より先に実行 |
| 更新 | `POST /api/room/management/update` | `_id`, `title`, `description`, `image_name`, 5設定フラグ, 元の`delete_flg` | 成功後に現在ページを再取得 |
| 削除・復元 | `POST /api/room/management/delete-state` | `_id`, `delete_flg` | 状態だけを変更し、成功後に現在ページを再取得 |

- 管理更新へ送る5設定フラグは`guest_reaction_only`、`member_only`、`room_display_hidden`、`notification`、`external_sns_button`である
- ページングルートはGET/POSTの両方を受け付けるが、現行フロントエンドはGETを使用する
- `/api/room/management/create`はバックエンドに存在せず、この画面にも作成導線はない。フロントエンドのルーム create アダプタも通常の`/api/room/create`だけを使用する
- 管理更新は対象ルームまたは所属フロアが物理的に存在しない場合に404を返す
- 401ではログアウトしてログイン画面へ遷移し、それ以外の失敗は処理別文言とAPIエラーコードに対応する翻訳済みの詳細をスナックバーへ表示する

### 読み込み中・データなし・エラー時

- 初回読込、更新中、空、取得失敗、前回結果を保った失敗、再試行は[管理一覧・検索共通仕様](../management-list.md)に従う
- 一覧取得の失敗は「ルームを読み込めませんでした」とAPIエラーコードに対応する翻訳済みの詳細を画面内に表示する
- 更新・画像処理の失敗は処理別文言とAPIエラーコードに対応する翻訳済みの詳細を共通ストアのスナックバーで通知する
