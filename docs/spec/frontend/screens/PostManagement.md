# 投稿管理（/management/post）

## 概要

- サイト全体の投稿、返信、投稿付加情報、返信付加情報をAdministratorが横断参照し、それぞれの論理削除状態を変更する
- 論理削除済みデータも表示し、この画面から復元できる
- 本文、ユーザ、ゲスト名、タグ、翻訳、リアクション、メディア内容の編集や物理削除は行わない

## 利用条件・開き方

- 入口はアプリメニューの管理者向け「投稿管理」、またはURLへの直接アクセスである

### URL

| 項目 | 値 |
| --- | --- |
| パス | `/management/post` |
| ルート名 | `PostManagement` |
| コンポーネント | `frontend/src/views/management/PostManagement.vue` |
| メタ情報 | `isManagement: true` |

- アプリメニューはVuex上のロールが`Administrator`の場合だけ「投稿管理」を表示する
- ルートガードはlocalStorageから状態を復元し、ログイン済みAdministratorだけを通過させる
- 未ログインまたはAdministrator以外が直接アクセスした場合はログアウト処理を行い、`/login`へ遷移する
- ルートメタ情報に画面タイトルはなく、文書タイトルにはアプリ名だけを設定する

### 利用条件

| 利用者 | アプリメニュー | 画面遷移 | 管理一覧・削除API |
| --- | --- | --- | --- |
| Administrator | 表示 | 可 | 可 |
| Editor／Author／developer | 非表示 | ログアウト後ログイン画面へ遷移 | 403 |
| ゲスト／未ログイン | 非表示 | ログイン画面へ遷移 | 401 |

- バックエンドはJWT検証時に有効なユーザと`session_version`を確認し、現在のDBロールで認証情報を上書きした後、ミドルウェアでAdministratorを確認する
- タイムライン管理サービスでは操作者ユーザを再取得せず、認可はJWT ミドルウェアと管理者ミドルウェアへ依存する
- 通常タイムラインで本人やフロア編集者が行う削除とは別の管理専用APIを使用する
- API契約は[タイムラインAPI](../../backend/api/timeline.md)、通常画面への反映は[Socket.IOイベント仕様](../../socket-events.md)を参照する

## 画面構成

- H1「投稿管理」
- 投稿を親単位で取得し、投稿、返信、付加情報を行として展開する一覧テーブル
  - コンテキスト: フロア名、ルーム名、ユーザ名またはゲスト名
  - 内容: 種別「投稿」「返信」「付加情報」と本文
  - 状態: 対象自身の有効／削除済み、親の削除による利用不可
  - 作成・更新・削除日時
  - 明示的な削除・復元操作
- 投稿を最上位とし、その下に返信と投稿付加情報、さらにその下に返信付加情報を表示する。字下げと境界線で階層を表す
- 行全体はクリックやキーボードの操作対象にせず、対象を示す明示ボタンだけで操作する
- 確認ダイアログは対象種別、本文、フロア／ルーム、ユーザ、現在状態を表示する
- 共通の一覧状態・ページャと、削除状態更新エラー用スナックバー
- 検索欄を表示する。フロア／ルーム／種別／期間の個別絞り込み、本文編集、複数選択、一括変更はない

## 操作と動作

### 初期表示・一覧・ページング

- 親ルームが存在しない投稿だけを抽出する機能はない

- 一覧の共通状態、検索フォーム、ページャ、URL履歴、競合要求、ページ補正は[管理一覧・検索共通仕様](../management-list.md)に従う
- 初期表示は`GET /api/chat/management/paginate?page=1&search=`を呼び出す
- 1ページ10件のChatを`created_at`降順で取得し、各Chatに内包する返信・付加情報を追加行としてすべて表示する。このため画面上の行数は10を超え得る
- 投稿、返信、投稿付加情報、返信付加情報は、それぞれの`delete_flg`にかかわらず取得・表示する
- 対象自身の論理削除は状態バッジで表す。親投稿または親返信が削除済みなら、状態欄には短い「利用不可」バッジを表示し、復元ボタンの近くに「親投稿または親返信を利用できません。」という詳細理由を表示する
- 各行のユーザ名はpopulate済みの`user.username`、ゲスト名、`—`の順で代替表示する
- バックエンドはフロア、ルーム、投稿ユーザ、返信ユーザ、投稿付加情報ユーザをpopulateする。返信付加情報ユーザはpopulateしないため、ゲスト名もなければ`—`を表示する
- フロアまたはルーム参照が欠損した場合は「参照先なし」を表示し、一覧と利用可能な行操作を継続する

### 検索

- バックエンド一覧APIは100文字以内の`search`を受け付け、次を大文字・小文字を区別せず、正規表現の特殊文字を通常文字として部分一致検索する
  - 有効ユーザのユーザ名に一致する投稿者、返信者、投稿付加情報作成者、返信付加情報作成者
  - 投稿または返信のゲスト名
- フロア名、ルーム名、本文、付加情報本文は検索対象ではない
- 論理削除済みユーザは名前検索の候補から除外するため、そのユーザのデータは名前で検索できない
- 現行画面は`ManagementListBase`の`searchEnabled`を有効にし、入力した検索語を`search`として一覧APIへ送る

### 削除状態ダイアログ

- 有効な対象は削除、削除済み対象は復元の確認ダイアログを開く。削除時は通常データが後から復元可能であることを表示する
- 対象種別、本文、フロア／ルーム、ユーザ、現在状態を確認文の下に表示する。対象が`image_name`、`video_name`、`audio_name`のいずれかを持つ場合、削除時は関連メディアを復元できない旨を警告する
- 送信ペイロードは`post_id`と`delete_flg`を必須とし、返信なら`reply_id`、付加情報なら`supplement_id`を加える
- `reply_id`と`supplement_id`を送る場合は返信付加情報、`supplement_id`だけなら投稿付加情報を対象とする
- `sending=true`の間は確定ボタンを無効にし、再度呼ばれても新しい要求を送らない
- 変更APIの開始から成功後の一覧再取得が終了するまで`sending=true`を維持し、進捗率を示さない処理中表示を行う
- 送信中はキャンセル、Escape、外側クリックを抑止し、ダイアログと投稿／返信／付加情報の選択対象を維持する
- 更新API成功時は現在ページの再取得が終了した後に`sending=false`とし、ダイアログと選択対象をクリアする
- 更新API失敗時は一覧を再取得せず、`削除に失敗しました`とAPIエラーコードに対応する翻訳済みの詳細を表示する。ダイアログと選択対象を維持したまま`sending=false`へ戻し、再操作を可能にする
- 更新API成功後の一覧再取得失敗は削除失敗として再表示せず、一覧エラーと再試行を`ManagementListBase`へ委ねる。再取得処理の終了後はダイアログと選択対象をクリアする
- 401では共通一覧処理がログイン画面へ遷移する

### 論理削除・復元と副作用

- 対象自身の`delete_flg`を指定値へ変更し、`updated_at`を現在日時へ更新する
- 削除時は`deleted_at`を現在日時、復元時は`null`へ変更する
- 投稿、返信、投稿付加情報、返信付加情報は独立して更新し、親を削除しても子のフラグは変更せず、有効な子の削除も可能である。ただし親が削除済みの子は復元ボタンを無効にし、先に親の復元が必要であることを関連付けて示す
- 削除時は対象自身へ直接設定された画像、サムネイル、動画、動画サムネイル、動画字幕、音声を、同じルームの有効データから参照されていない場合だけ物理削除する
- 投稿または返信を削除しても、内包する付加情報のメディアは削除しない
- メディア参照確認に失敗した場合と、ファイル削除でENOENT以外のエラーが発生した場合はエラーを記録してファイルを保持し、論理削除処理は継続する
- 復元ではDB上の本文、タグ、翻訳、リアクション、メディアファイル名を維持するが、物理削除済みファイルを復元しない。復元後もメディアURLが404または再生不能になり得る
- 管理削除はSocket.IOイベント、プッシュ通知、接続中タイムラインへの再取得要求を送らず、製品内の操作履歴も記録しない

## 通信・エラー時の動作

### 使用するAPI

| 目的 | Method / Path | 主な送信値 | 画面での扱い |
| --- | --- | --- | --- |
| ページング一覧 | `GET /api/chat/management/paginate` | クエリ: `page`, `search` | `docs`, `total`, `pages`, `page`を一覧とページャへ反映 |
| 論理削除状態更新 | `POST /api/chat/management/delete` | 本文: `post_id`, 任意の`reply_id`／`supplement_id`, `delete_flg` | 成功後に現在ページを再取得 |

- ページングルートは`router.all`のため複数Methodを受け付けるが、現行フロントエンドはGETを使用する
- 更新APIは変更後Chatを返すが、画面は応答データによる行置換を行わず一覧を再取得する

### 読み込み中・データなし・エラー時

- 初回読込、更新中、空、取得失敗、前回結果を保った失敗、再試行は[管理一覧・検索共通仕様](../management-list.md)に従う
- 一覧取得の失敗は画面内に表示し、投稿・返信・付加情報の削除状態更新失敗はスナックバーで通知する
- 削除状態更新中と成功後の一覧再取得中は、ダイアログ内で同じ処理中表示を継続して表示する
