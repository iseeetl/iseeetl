# 管理一覧・検索共通仕様

## 概要

`ManagementListBase`を使う13画面に、一覧の取得状態、検索、ページ送り、表の名前付けの共通契約を適用します。
`QuickTextManagement`は階層全件表示のため、この共通一覧を使用しません。
各画面の検索対象、入力長、API、権限、一覧行、作成・編集・削除・出力は
[画面仕様](screens/README.md)で定義します。利用者向けの操作は
[管理画面マニュアル](../../manual/management/README.md#共通する一覧操作)を参照してください。

## 動作・適用条件

### 一覧の表示状態

| 状態 | 表示と操作 |
| --- | --- |
| 未取得 | `autoFetch=false`で取得または`setItems`前は、空状態を表示しない |
| 初回取得中 | 「読み込み中です」を表示し、一覧表とページャはまだ表示しない |
| 1件以上 | 総件数、現在ページ／全ページ、一覧表、2ページ以上の場合はページャを表示する |
| 0件 | 通常は「データがありません」、検索適用中は「条件に一致するデータがありません」を表示する |
| 再取得中 | 前回の成功結果を残し、「更新中です」を表示する。検索、ページャ、再試行は無効にする |
| 初回失敗 | 画面内のエラーと「再試行」を表示し、一覧表、空状態、ページャは表示しない |
| 再取得失敗 | 前回結果とエラーを残し、「前回取得した結果を表示しています」と再試行を表示する |

- 結果領域は`role="region"`、既定ID`management-list-results`、翻訳済みの操作名を持ちます。
- 結果領域と`.view`の`aria-busy`を同期し、取得中の状態文言を`role="status"`で通知します。
- 一覧取得の失敗は画面内の`role="alert"`だけで通知し、スナックバーへ二重通知しません。
  作成、編集、削除、出力などの画面固有操作はスナックバーを使います。
- `ManagementListBase`内のスナックバーは既定で`role="alert"`、`aria-live="assertive"`、
  `aria-atomic="true"`を持ち、画面固有操作のエラー全体を支援技術へ通知します。
- 401はログアウト後にログイン画面へ遷移します。それ以外のエラーは画面固有の取得失敗文言と、
  [共通エラー処理](error-handling.md)に従い、APIエラーコードに対応する翻訳済みの詳細を表示します。
- 古い要求の成功、エラー、終了処理は画面へ反映しません。
- 応答の最終ページよりURLの`page`が大きい場合は、最終ページ（0件なら1）へURLを
  `replace`し、1回だけ再取得します。

### 検索

- 検索欄と状態絞り込み条件を併用する画面では、PCで同じ検索条件行の左に状態絞り込み条件、右に検索欄を
  横並びにし、狭い画面では状態絞り込み条件、検索欄の順に縦積みする。作成、CSV入出力など検索条件ではない操作は、
  検索条件行へ混在させない。
- 検索欄はブラウザ標準の`<form role="search">`と`type="search"`の入力欄を使います。
- 検索ボタンはアイコン付きの主要操作として表示し、フォーム送信で1回だけ検索します。
  IMEの文字変換中と取得中は送信しません。
- 入力値がある場合だけ「クリア」ボタンを表示します。クリアは`q`を削除してページ 1を取得し、
  完了後も検索入力欄へフォーカスを戻します。明示ボタンは中立色とし、重複するブラウザ標準の検索入力欄の
  取消操作は表示しません。
- 入力中の値と送信済みの値を分けます。検索せずにページを移動しても、未送信の値はAPIへ送られません。
- 画面固有の最小／最大文字数を満たさない場合は、URL、現在ページ、適用済み値、API要求を変更しません。
- URLの`page`と`q`を復元し、ブラウザの戻る・進むも同じ条件で取得します。
  ページだけの履歴変更では未送信の入力値を残し、`q`が変わったときだけ入力欄へ同期します。
- 検索値の前後の空白除去と検索対象は各画面と対応するバックエンドAPI仕様で定義します。

### ページ送り

- ページャは翻訳済みの名前を持つ`nav`です。先頭、前、最大5件の数値ページ、次、最後の操作を表示します。
- 現在ページは無効と`aria-current="page"`で示します。範囲外、現在ページ、取得中の操作は発火しません。
- 1ページ以下ではページャを表示しません。狭い画面ではボタンの文字を潰さず折り返します。
- 検索入力欄、検索・クリアボタン、ページャは`aria-controls`で同じ結果領域を参照します。
- キーボードフォーカスは共通`:focus-visible`の表示を使います。

### 表、状態、行操作

- 各画面は翻訳済みの`tableLabel`を渡し、一覧表スロットが受け取る`tableAttrs`をブラウザ標準の
  `<table>`へ適用します。`tableLabel`未指定時は画面タイトルを表の名前に使用します。
- 一覧行自体はクリック、キーボード、`role`、`tabindex`による操作対象にしません。編集、削除、復元、
  メンバー削除、詳細表示、ダウンロードは、対象名を含むアクセシブルな名前を持つ明示ボタンから行います。
- 同じ行に削除と編集がある場合は、通常のフロア／ルーム一覧と同じく「削除」「編集」の順で
  横並びにする。文字を持つ行操作は塗りつぶしボタンとし、狭い列でもボタン自体を縦積みしたり
  文言を1文字ずつ折り返したりしない。
- 一覧表は表示領域内へ収め、一覧領域に横スクロールを発生させません。十分な幅ではブラウザ標準の一覧表を表示し、
  1100 CSS px以下では各行をカードとして表示します。カードには各セルの列名を値の上へ表示し、ブラウザ標準の
  `table`、`thead`、`th scope="col"`、`tbody`の意味構造は維持します。
- 一覧表の見出しは語中で縦書きのように折り返しません。メール、長い名称、本文などの値はカードまたは
  セル内で折り返します。削除と編集など同じ行の操作ボタンは横並びを維持します。
- 未設定のメール、追加指示、更新日、削除日など、値が存在しない一覧表セルは空欄にせず`—`を表示する。
- 論理削除を扱うフロア、ルーム、ルームタグ、ユーザの一覧は、
  「すべて」「未削除」「削除済み」の状態絞り込み条件を表示します。初期値は「すべて」です。
  クエリの`delete_flg`は未削除で`false`、削除済みで`true`とし、すべてでは省略します。
- 状態絞り込み条件の変更は適用済み検索語を維持して`page=1`から再取得します。URLの検索クエリは
  変更せず、取得結果だけを選択した状態へ切り替えます。
- ライフサイクル、表示／非表示、公開／メンバー限定、親状態による利用不可は`ManagementStatusBadge`の翻訳済み文言で示し、色を補助表現として使います。
- `.soft-delete`を使用する画面では、削除済み行を中立的な灰色背景と通常の可読文字で表示します。
  状態の判別には状態バッジと削除日時を併用します。

### 論理削除・復元の確認

- 一覧の論理削除・復元は、対象種別と対象名を示す`ManagementLifecycleDialog`で確認します。
  削除確定はdanger、復元確定はprimaryとします。削除時は既定で後から復元可能であることを表示し、
  復元操作を提供しない画面が削除確認だけに再利用する場合は復元案内を表示しません。
- PCではキャンセルと確定操作を右下へ隣接して配置し、モバイルではフッターを表示せず、ヘッダー左の
  キャンセルとヘッダー右の確定操作へ切り替えます。
- 画面は必要に応じて対象詳細と警告を追加します。投稿管理は対象種別、本文、フロア／ルーム、ユーザ、
  現在状態を表示し、添付メディアを持つ対象の削除時はファイルを復元できない旨を警告します。
- 変更APIの開始から成功後の一覧再取得が成功または失敗で終了するまで対象とダイアログを維持し、二重送信、キャンセル、
  Escape、背景クリックを抑止します。変更APIの失敗時は対象を維持して再操作を可能にします。
- 成功時は現在ページを再取得してからダイアログを閉じます。一覧再取得のエラー表示は共通一覧へ委ねます。
- 共通・フロアタグとAI解析設定は物理削除の確認に`ManagementLifecycleDialog`を使用し、復元案内を非表示にして復元できないことを表示します。
- 物理削除を行うフロア／ルームメンバー、Spam、単語は、それぞれの画面固有確認ダイアログと
  復元不能である旨の契約に従います。

### 公開契約と画面固有操作

- `header`、`actions`、`filters`、`table`、`dialogs`のスロットと、一覧表スロットの`items`、`fetching`、
  `currentPage`、`lastPage`、`total`、`tableLabel`、`tableAttrs`を公開します。
- `header`と`actions`は一覧取得中の`fetching`を受け取ります。画面全体に対する作成操作は
  `header`でH1の反対側へ置き、CSV入出力などの補助操作は`actions`で検索条件と分離する。
- `filters`は検索欄と同じ検索条件領域に画面固有の表示条件を置く場合に使用し、同じ`fetching`を
  受け取ります。配置は[検索](#検索)に従います。
- `reload()`は現在のページと適用済み検索で取得し、Promiseを返します。
- `reloadFromFirstPage()`は適用済み検索を維持してページ 1へ移動・再取得し、Promiseを返します。
- `setItems(items)`は一覧エラーを解除して成功済み状態としますが、ページ情報は変更しません。
- `replaceItem(item)`は同じ`_id`の行だけを置き換え、件数とページ情報を変更しません。
- `actions`と`table`内の画面固有操作は共通一覧から一律に無効にしません。
