# 認証処理の競合と復旧

## 概要

ログイン・登録・パスワード再設定が重複した場合や、途中で失敗した場合の処理を説明します。

## 動作・適用条件

### LINE初回ログイン

認証済みのLINE利用者について、`AuthIdentity`の`provider + provider_user_id`一意制約で認証先User IDを先に予約します。`provisioning: true`の間は予約したUserの作成を再開でき、完了後に`false`へ変更します。並行要求は同じ予約を使用し、確定した認証情報の有効なUserだけにログイン用JWTを発行します。

既存の有効なメール一致Userは維持します。メール一意制約に競合した場合は確定済みUserを読み直し、認証情報の紐付けを確定します。メールなしの同時ログインも予約IDが同じなのでUserは1件です。User作成後に処理が止まっても、そのUserを再利用し、新しいUserを追加しません。削除済みの紐付け先は再作成・再有効化しません。

前提はAuthIdentityの一意索引と[ユーザメールの一意索引](user-mail-index.md)です。認証情報と紐付いていないUserの削除・統合は自動で行いません。

### ユーザ有効化

本User作成時に、元の有効化トークンのSHA-256と有効期限を同じUserレコードへ保存します。トークン原文は本Userへ保存せず、これらの内部フィールドは通常のUser検索応答から除外します。

本登録成功後のUserTemp削除が失敗すると初回要求は失敗しますが、有効期限内に同じURLを再読込すると、同じトークン由来の有効Userを照合して後処理を再開します。後処理完了後の同じ要求も期限内は成功します。本登録時点で固定した期限は再試行で延長しません。

同時要求がUserのメール一意制約に競合しても、同じトークン由来なら成功したUserを使用します。別トークン・無関係な既存Userをメール一致だけで成功扱いにはしません。処理は自動ログインせず、パスワードや既存Userの状態を再更新しません。

仮登録のメール送信が失敗してもUserTempは残ります。同じメールで複数回仮登録した場合のUserTempも自動統合しません。

### パスワード再設定

新規リンクは48文字のランダムトークンを使います。SMTP送信に成功してから、Userの非公開`password_reset`へSHA-256・発行先メール・期限・未消費状態を確定します。送信失敗時は、この要求によって旧リンクを置き換えません。トークン原文・暗号化トークン・配送待ち記録をDBに保存せず、画面から再要求した場合は別の新しいトークンを発行します。

送信開始時のメール・セッション世代・再設定状態が維持され、有効Userかつ新リンクの期限内の場合だけ条件付きで確定します。同じ状態からの並行要求は先に確定した1件だけ成功し、遅れて完了した送信がそのリンクを置き換えることはありません。送信中に旧リンクで再設定した場合も、消費済み状態を復活させません。

送信APIはSMTP送信とDB確定が成功した場合だけ200、送信失敗・競合・DB確定失敗は500を返します。未登録メールへの200応答は維持します。SMTP送信とDB確定には時間差があり、送信後にDB確定が失敗した場合、届いた新リンクは使えません。利用者は画面から再要求します。DB更新の応答だけが失われた場合は新リンクが有効になっている可能性があります。メールの到着順と有効なリンクの順序は保証しません。

メールの自動再配送や再送コマンドはありません。`password_reset_delivery`と`password_change_notice`は通常応答から除外する互換フィールドとして定義しますが、読み書き・再送・自動削除には使用しません。平文トークン・URL・宛先・メール本文はログへ出力しません。

確定APIはトークンの一致・未消費・期限内・有効Userを条件に、パスワード、消費済み状態、`session_version`の加算を同じUser更新で確定します。更新前の失敗ではリンクを消費せず、同じリンクで再試行できます。同時実行と再利用は1回だけ成功します。成功応答を受け取れなかった場合も、確定済みトークンは再利用できません。

`ResetPassword`コレクションに保存されたリンクはUserに新状態がない場合だけ受け付け、元の有効期限を維持して状態を条件付き移入します。新規発行や消費後は旧リンクへ戻りません。旧レコードの回収失敗は成功を覆さず、残っていても再利用できません。再設定の発行・配送・検証・確定は同じバージョンのバックエンドで行います。MongoDBトランザクションは使用しません。

Userの`users_password_reset_token_hash`は、再設定トークンのハッシュ照合に使う非一意・sparse索引です。[Userモデルの定義](user-mail-index.md)から起動時に自動作成し、作成完了後に受付を開始します。同時更新の防止は、索引とは別に更新条件で保証します。

### パスワード変更・再設定の通知

本人のパスワード変更と再設定では、パスワード・セッション世代の更新と旧セッションの失効を完了してから、更新後のUserの宛先・保存済み言語で通知を1回試行します。通知失敗は変更成功を覆さず、APIは成功の200（変更は空オブジェクト、再設定は`OK`）を返します。変更画面はログアウトしてログイン画面へ進み、再設定画面は成功を表示します。

未送信通知記録は保存せず、後日の再配送は行いません。通知失敗時は接続先・宛先・本文を含まない固定コードだけをログへ渡します。通知前のプロセス停止や配送障害で届かなかった通知を復旧する保証はありません。メール機能無効時は送信しません。

接続・挨拶の待機は各10秒、SMTP無通信待機は30秒です。通知処理は認証状態を更新せず、パスワードとセッション世代を再変更しません。
